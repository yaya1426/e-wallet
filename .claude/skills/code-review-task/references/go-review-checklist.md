# Go + e-wallet review checklist

Sources: Effective Go, Go Code Review Comments (go.dev/wiki/CodeReviewComments), Go Doc
Comments, and this project's TDRs / architecture. Each item names what a finding should cite.

## A. Architecture and boundaries (architecture.md §3, TDR-001, TDR-012)
- [ ] Files are in the right place per TDR-012 layout (`cmd/`, `internal/<module>/`, `internal/platform/`, `migrations/`, `api/`, `test/`).
- [ ] Imports follow the allowed directions in architecture §3.2; no cycles; `ledger` and `platform` import no business module.
- [ ] A module reads/writes **only its own tables** (data-model §1). No SQL on another module's tables.
- [ ] Other modules are used only through their exported service API — no reaching into internals, repositories or sqlc types of another module.
- [ ] `platform` packages contain no business rules; business modules contain no generic infrastructure.
- [ ] Handlers → service → repository. Handlers have no SQL and no business rules; repositories have no business rules.
- [ ] **No abstraction leakage:** pgx/sqlc types, HTTP types (`*http.Request`, status codes) or bank-adapter DTOs do not cross module boundaries; the `bank.Gateway` callers never see HTTP details; domain errors are mapped to HTTP only in the HTTP layer.
- [ ] Interfaces are defined by the consumer, are small, and exist only where there are ≥2 implementations or a test seam is needed (no speculative interfaces).

## B. Money and correctness (TDR-003, 004, 005, 006, 007, 010)
- [ ] Money is `int64` piasters / `money.Money`; no `float32/float64`, no `strconv.ParseFloat`, no decimal JSON.
- [ ] Overflow-checked arithmetic; currency checked.
- [ ] Postings only via `ledger.Post`; every entry balances; correct accounts and directions per TDR-004 §3; `(transaction_id, entry_type)` uniqueness respected.
- [ ] State change + ledger + outbox in **one** `db.InTx`; no network/bank call inside a DB transaction.
- [ ] Row locks before balance checks; ascending ID order; `lock_timeout`; retry on 40001/40P01.
- [ ] Idempotency: key required, request hash compared, response replayed; bank key = transaction ID; webhook dedupe; terminal states never changed.
- [ ] Transaction state transitions only via the state machine (`Transition(from, to)`).
- [ ] Reconciliation never auto-fixes contradictions; discrepancies recorded.

## C. Go code standards
- [ ] `gofmt`/`goimports` clean; `go vet` and `golangci-lint` clean.
- [ ] **Naming:** MixedCaps, no underscores; package names short, lower-case, singular, no `util/common/helpers`; no stutter (`ledger.Entry`, not `ledger.LedgerEntry`); initialisms consistent (`ID`, `HTTP`, `URL`, `IBAN`); receiver names short and consistent, never `this/self`; getters without `Get` prefix; error vars `ErrXxx`, error types `XxxError`; boolean names read as questions (`isTerminal`, `hasKey`); variable name length proportional to scope.
- [ ] Names say the business meaning (`availableBalance`, `reserveEntry`) — not `data`, `info`, `tmp`, `obj`, `res2`.
- [ ] Exported identifiers have doc comments starting with the name; comments explain *why*, not *what*.
- [ ] Errors: returned not panicked; wrapped with `fmt.Errorf("…: %w", err)`; lower-case, no punctuation; checked with `errors.Is/As`; never ignored (`_ =`) without a comment; no logging **and** returning the same error.
- [ ] `context.Context` is the first parameter, never stored in structs, propagated to DB and HTTP calls; timeouts set for outbound calls.
- [ ] Goroutines: every one has an owner, a stop path (ctx) and is waited for (errgroup/WaitGroup); no leaks; channels closed by the sender; no unbounded goroutine creation.
- [ ] Concurrency: shared state guarded; tests run with `-race`.
- [ ] No global mutable state; dependencies injected through constructors; no `init()` side effects.
- [ ] Functions small and single-purpose; early returns over deep nesting; no dead code, no commented-out code, no TODO without a task ID.
- [ ] Zero values useful; no needless pointers; slices pre-sized when length known; `defer rows.Close()` / `resp.Body.Close()`.
- [ ] Config from env via `config`; no hard-coded secrets, URLs, limits.
- [ ] Logs: `slog` with structured fields (`transaction_id`, …); no secrets/PII (passwords, full IBAN, tokens) in logs.

## D. Data and API
- [ ] Migrations are golang-migrate `NNNNNN_name.up.sql` + `.down.sql` pairs (TDR-014), forward-safe, with constraints from the data model (CHECKs, UNIQUEs, FKs, indexes).
- [ ] SQL in `queries.sql`, generated by sqlc; no string-concatenated SQL.
- [ ] API follows TDR-013: paths, `snake_case`, `amount_minor`, error body, status codes, strict decoding, body size limit; matches `api/openapi/wallet.yaml`.

## E. Tests
- [ ] Every AC has a test; business rejections, boundaries, duplicates, concurrency and failure cases covered.
- [ ] Tests are deterministic (fake clock, no sleeps for sync), independent, table-driven where natural, with clear names.
- [ ] Integration tests use testcontainers and assert ledger integrity.
- [ ] No skipped/weakened tests.

## Severity
| Severity | Use for | Blocks approval? |
|----------|---------|------------------|
| **Blocker** | Wrong money/ledger behaviour, data-loss/duplication risk, boundary violation, security issue, failing lint/tests, AC not met | yes |
| **Major** | Abstraction leakage, wrong package placement, missing tests for a business case, error handling gaps, goroutine leak risk | yes |
| **Minor** | Naming, readability, small duplication, missing doc comment | no |
| **Nit** | Style preference | no |
