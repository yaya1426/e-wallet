# TDR-005 — Idempotency Keys (API and Bank)

| Field      | Value |
|------------|-------|

## Context
Users double click, mobile networks drop responses, clients retry. Workers retry bank calls.
Banks re-send webhooks. Every one of those must move money **at most once**.

## Decision — four layers of protection

### Layer 1: API idempotency (client → wallet)
- Header `Idempotency-Key` **required** on `POST /v1/topups`, `/v1/withdrawals`, `/v1/transfers`.
  Format: UUID (any version), max 64 chars. Generated by the client per user action (not per
  HTTP attempt).
- Table `idempotency_keys`:
  `user_id, key, method, path, request_hash (SHA-256 of canonical JSON body), status
  (IN_PROGRESS | COMPLETED), response_status, response_body JSONB, transaction_id, created_at,
  expires_at` with `PRIMARY KEY (user_id, key)`.
- Algorithm (implemented as HTTP middleware + a store in `internal/idempotency`):
  1. `INSERT … ON CONFLICT DO NOTHING` the key as `IN_PROGRESS` — **in the same DB transaction
     as the business work**.
  2. If the insert hit a conflict, read the existing row:
     - different `request_hash` → `422 IDEMPOTENCY_KEY_REUSED`;
     - `COMPLETED` → replay stored `response_status` + `response_body` (header
       `Idempotent-Replayed: true`);
     - `IN_PROGRESS` → `409 REQUEST_IN_PROGRESS` (client retries later).
  3. Business work + saving the response + marking `COMPLETED` all commit together.
     If the business work fails with a **validation/business error** (4xx), the response is
     stored too (same key → same error). On **5xx / crash** the transaction rolls back and the
     key disappears, so the client can safely retry.
  Because the key row is part of the business transaction, two concurrent requests with the
  same key serialize on the primary key: the second one waits on the uncommitted insert, then
  sees `COMPLETED` and replays. The wait is bounded by `SET LOCAL lock_timeout = '2s'`; on
  timeout the second request gets `409 REQUEST_IN_PROGRESS`. (So `IN_PROGRESS` is never
  visible as a committed row in this design; the status column exists for clarity and for a
  possible future split into two DB transactions.)
- Retention: `expires_at = created_at + 24h`; a cleanup goroutine deletes expired rows hourly.

### Layer 2: Transaction uniqueness (permanent)
- `transactions` has `UNIQUE (initiator_user_id, idempotency_key)` kept forever, so even
  after the 24 h key expires, a very late retry cannot create a second transaction.

### Layer 3: Outbound idempotency (wallet → bank)
- Every bank call carries `Idempotency-Key: <transaction_id>`. Retries reuse it. The bank
  (and our simulator) return the original result for a repeated key.
- When we do not know if a call succeeded (timeout), we **retry or query by that key**; we
  never generate a new key for the same transaction.

### Layer 4: Inbound idempotency (bank → wallet webhooks) and ledger guard
- Webhook inbox `UNIQUE (provider, provider_event_id)` drops duplicate deliveries (TDR-007).
- State machine: a terminal transaction ignores a repeated identical outcome.
- Ledger: `UNIQUE (transaction_id, entry_type)` (TDR-004) makes double-posting impossible
  even if all other layers had a bug.

## Alternatives Considered
| Option | Why not chosen |
|--------|----------------|
| Optional idempotency key | Clients forget it; money endpoints must be safe by default. |
| Redis-based key store | Not atomic with the business commit; window for duplicates. |
| Dedup by payload hash only (no key) | Two legitimate identical transfers would be blocked. |

## Consequences
- + Effectively-once money movement end to end.
- − Clients must generate and keep a key per action (documented in API spec).
